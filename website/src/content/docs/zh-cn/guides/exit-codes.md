title: 退出码

---

| 退出码 | 含义 |
| --- | --- |
| `0` | 成功 |
| `1` | 断言失败（某个重放用例的期望未成立） |
| `2` | 用法或配置错误（错误的参数/配置、未解析的密钥或 target、CI 中 heal 被阻止） |
| `3` | 环境错误（浏览器启动失败、AI 提供方不可用、文件 I/O 失败、意外崩溃、被中断） |
| `4` | 执行计划或定位缓存产物不可信（缺失、`inputsDigest` 过期、1:1 对应关系被破坏）—— 需先重新生成再信任结果 |
| `5` | 选择结果零匹配（可用 `--allow-empty` 关闭此行为） |

当一个批次中的结果落在多个类别时，最终报告的进程退出码取优先级最高的那个，固定顺序为：

**2 > 3 > 4 > 1 > 5 > 0**

每个用例各自的结果始终完整保留在 JSON 报告的 `results`/`errors` 中。

<details>
<summary>为什么是这个顺序？</summary>

这个顺序按“进程结果应在多大程度上主导混杂批次”排列，而不是按数值大小排列：

- **2（用法/配置）**和 **3（环境）**优先级最高 —— 如果调用本身配置有误，或环境根本无法运行，批次中的其他任何结果都同样不可信。
- **4（不可信的产物）**次之：过期或损坏的计划意味着批次的结果并不反映当前的提示词。
- **1（断言失败）**只有在运行本身已知可信时才会胜出。
- **5（零匹配）**排在真实断言失败之下 —— 一个什么都没找到去测试的批次，比一个找到了东西但测试失败的批次信号更弱。
- **0（成功）**是空输入或全部成功输入的兜底结果。

这一顺序是在代码中强制执行的，而不仅仅是文档说明：`src/usecases/exit-code-priority.ts` 中的 `selectExitCode` 维护了一张优先级表，并在模块加载时断言这些优先级构成一个没有空隙或并列的连续序列。
</details>

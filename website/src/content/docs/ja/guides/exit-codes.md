| コード | 意味 |
| --- | --- |
| `0` | 成功 |
| `1` | アサーション失敗（リプレイされたケースの期待値が成立しなかった） |
| `2` | 使用方法または設定エラー（不正なフラグ/config、未解決のシークレットまたはターゲット、CI での heal ブロック） |
| `3` | 環境エラー（ブラウザ起動失敗、AI プロバイダ利用不可、ファイル I/O 失敗、予期しないクラッシュ、中断） |
| `4` | プランまたはグラウンディングの成果物が信頼できない（欠落、`inputsDigest` が古い、1:1 対応が壊れている）— 結果を信頼する前に再生成が必要 |
| `5` | 選択条件が 0 件のプロンプトにマッチした（`--allow-empty` で無効化可能） |

バッチの結果がこれら複数のカテゴリにまたがる場合、報告されるプロセスの終了コードは次の固定順位のうち最も優先度が高いものになる:

**2 > 3 > 4 > 1 > 5 > 0**

個々のケースの結果は、常に JSON レポートの `results`/`errors` に保持される。

<details>
<summary>この順序である理由</summary>

この順序は、数値の重大度ではなく、混在するバッチにおいてプロセスの結果がどれだけ全体を支配すべきかでランク付けしている:

- **2（使用方法/設定）** と **3（環境）** は他のすべてより優先される — 呼び出し自体の設定が誤っていた、または環境が実行できなかった場合、バッチ内の他のどの結果も信頼できないため。
- 次に **4（信頼できない成果物）**: 古い、または壊れたプランは、バッチの結果が現在のプロンプトを反映していないことを意味する。
- **1（アサーション失敗）** は、実行そのものが信頼できると判明して初めて優先される。
- **5（0 件マッチ）** は実際のアサーション失敗より下位にランクされる — 何もテスト対象を見つけられなかったバッチは、何かを見つけて失敗したバッチより弱いシグナルであるため。
- **0（成功）** は、空またはすべて成功した入力に対するフォールバックである。

これはドキュメント化されているだけでなく、コードでも強制されている: `src/usecases/exit-code-priority.ts` の `selectExitCode` はランクテーブルを保持し、モジュール読み込み時にランクが欠番や同順位のない連続した並びを成しているかをアサートする。
</details>
